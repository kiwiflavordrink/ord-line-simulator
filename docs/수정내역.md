# 계산 수정 내역 (2.305 구조 + 2.323 툴팁 수치)

## 원칙

- 복호화된 맵은 2.305뿐이다. 2.323 수치는 ORDR.kr 툴팁(`dist/ordr_units.json`, 2026-10-14 수집)에서 가져온다.
- **구조는 2.305 맵, 수치는 2.323 툴팁**. 구조란 발동 방식·대상·범위/단일·피해 타입·자원 규칙·변신 방식, 수치란 계수·고정 피해·확률·쿨·체력 비율이다.
- 툴팁에 수치가 없으면 2.305 값을 `[2.305 기준]`으로 쓴다. 둘 다 없으면 `[추정]`.
- 근거 표기: `[툴팁 코드]` = `dist/ordr_units.json`의 해당 유닛 문장, `[2.305 j:줄]` = `war3map.j`, `[2.305 wts:줄]` = `war3map.wts` (`dist/resources/maps/s2-2305-extracted.zip` 압축 해제 기준 줄 번호).
- 결과 비교: `node scripts/hero_results.mjs docs/results/<단계>.json`. 기본 옵션(방깎 201, 범위 적중 100%, 레드포스호·자원 만충·소환 포함), 각 유닛 1기·3기의 60~65라 라운드별 잔존 수. 수정 전 기준은 `docs/results/00_baseline.json`(main `aa6ff9d`).

### 42. 보유 패 자동 인식 1단계: 읽기 전용 메모리 진단

헬퍼 기록이 꺼져 있고(`DetailedPlayLogging false`), 맵 세이브(`CustomMapData\ORDR2\`, 2.305 j:15352)에는 진행 중인 패가 없다. 그래서 오버레이가 패를 직접 읽도록 워크3 메모리 구조를 찾는다. `tools/memscan/memscan.ps1`은 유닛 코드(4바이트 정수)가 나온 주소와 주변 바이트를 저장하는 읽기 전용 진단이다. 유닛 객체 배치는 게임 클라이언트가 정하므로 맵 패치가 아니라 클라이언트 패치 때 다시 확인한다. 계산 엔진은 바뀌지 않는다.

두 번 스캔(나미+상디 → 로빈 조합 전후) 결과, 유닛 기록은 코드 뒤에 색 이름 문자열이 붙은 구조이고 코드 앞 48바이트 상태값으로 배치(0x46·0x47)·원형(0x48)·사라짐(0x11)을 구분할 수 있었다. 조합으로 사라진 나미·상디만 0x11로 바뀌었고 나머지는 그대로였다. 이를 이용해 코드 입력 없이 보유 패를 세는 `hand.bat`(`memscan.ps1 -Hand`)을 추가했다.


### 43. 오버레이: 게임 메모리에서 보유 패 자동 읽기

`tools/memscan/memscan.ps1 -Watch`가 처음에 전체 메모리를 훑어 내 유닛 기록이 있는 구역을 기억하고, 그 뒤로는 그 구역만 3초마다 다시 읽어(90초마다 전체 재확인) `{Status, Units:[{Rawcode(뒤집힌 표기), Code, Count, Owner, Name}]}`를 파일로 쓴다. 오버레이 입력에 "게임에서 자동 읽기"를 추가해 이 파일을 2초마다 읽고 기존 계산(`dist/advisor.mjs`)에 넣는다. 유닛 기록 판별: 코드 바로 뒤 `|c`+16진 8자리 이름, 코드 앞 72바이트 값 1, 주인 = 플레이어 번호, 사라진 기록(앞 48바이트 0x11 또는 앞 88바이트 −1) 제외. 실제 게임 기록(6라운드, `흔함` 통계와 9종 일치) 바이트로 만든 가짜 메모리로 C# 판별과 -Watch 루프를 확인했다. 계산 엔진은 바뀌지 않는다.
